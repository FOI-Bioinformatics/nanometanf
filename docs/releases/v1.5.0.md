# Release v1.5.0 -- Streaming Kraken2 Architecture

**Type:** Minor release -- architectural change to the real-time path
**Status:** Released; recommended production version
**nf-core compliance:** 96/100

---

## Summary

v1.5.0 replaces the global-serialisation Kraken2 path used in v1.3.x
with a streaming architecture that scales with barcode count. The
previous architecture set `maxForks 1` on the merger and report
modules, re-read the entire cumulative output on every batch, and had
no backpressure -- which capped CPU utilisation at roughly 15-20% and
throughput at about 10-15 files / second once a run exceeded ten
barcodes.

Internal benchmarks measure roughly four to five times higher
throughput on runs with 12+ barcodes after this change.

The streaming path is enabled by default for real-time runs; existing
batch workflows are unaffected.

---

## Architectural changes

### Per-sample parallelism

The `KRAKEN2_OUTPUT_MERGER` and `KRAKEN2_REPORT_GENERATOR` modules no
longer have `maxForks 1` set globally. Each sample runs independently,
so concurrent samples no longer queue behind one another.

### Append-only batch storage

Each Kraken2 batch is now written to its own file under the sample
directory:

```
outdir/kraken2/{sample_id}/
|-- batches/
|   |-- batch_0.kraken2.output.txt
|   |-- batch_1.kraken2.output.txt
|   `-- ...
|-- batch_reports/
|   |-- batch_0.kraken2.report.txt
|   `-- ...
|-- index.json                       # Atomic batch manifest
|-- taxid_counts.json                # Incremental taxid state
`-- stats/
```

Cumulative `{sample_id}.cumulative.kraken2.{output,report}.txt` files
are produced once per sample at end of session by
`KRAKEN2_FINAL_AGGREGATOR`. The dashboard reads the per-batch reports
during the run; downstream tools that need a single cumulative file
get it once the run completes.

This changes per-batch I/O from O(cumulative size) to O(batch size).

### Incremental taxid counting

`KRAKEN2_REPORT_GENERATOR` maintains a `taxid_counts.json` state file
per sample and updates it incrementally per batch, instead of merging
the full cumulative output on every batch. Atomic state writes
(`os.rename` of a temp file) prevent partially-written state being
read.

### Backpressure controls

Two parameters bound the in-flight work:

```bash
--max_concurrent_batches 4     # Per-sample backpressure limit
--max_classification_forks 8   # Pipeline-wide cap on concurrent Kraken2 jobs
```

The defaults suit a 16-core / 64 GB workstation. Tune downward for
smaller hosts or upward for cluster nodes.

---

## New parameters

| Parameter                      | Default | Purpose                                                         |
| ------------------------------ | ------- | --------------------------------------------------------------- |
| `--kraken2_enable_incremental` | `true`  | Use the streaming path. Set `false` to force the legacy merger. |
| `--max_concurrent_batches`     | `4`     | Backpressure: max batches in flight per sample.                 |
| `--max_classification_forks`   | `8`     | Cap on concurrent Kraken2 jobs across all samples.              |
| `--kraken2_sync_interval`      | `10`    | Number of batches between cumulative-report regenerations.      |

## Other changes shipped in v1.5.0

- **Unified input handling** via the new `INPUT_SCANNER` subworkflow
  and the `InputDetector` helper in `lib/`. The new `--input_dir`
  parameter auto-detects flat versus barcoded layouts. The legacy
  `--barcode_input_dir` is deprecated but still accepted.
- **`BatchUtils` refactor**: replaced the deprecated `Channel.create()`
  with `buffer()` operators throughout the real-time path.
- **`FASTP_STREAMING` local module** for multi-file concatenation in
  `watchPath` mode. The upstream `nf-core/fastp` module is restored
  unchanged for batch runs.
- **Test suite**: 55 active tests (17 pipeline + 38 module),
  stub-mode compatible.

---

## Breaking changes

None for standard usage.

The Kraken2 output directory layout has moved to per-sample
subdirectories with `batches/` and `batch_reports/`. Tools that
depended on the old flat structure
(`results/kraken2/{sample}.kraken2.report.txt`) will continue to find
the cumulative file at end of session, but in-flight tools should
read from `batch_reports/` instead.

## Migration

From v1.2.0 or v1.3.x: pull v1.5.0, re-run with the same parameter
set. The new concurrency parameters are optional. See
[`MIGRATION_GUIDE.md`](MIGRATION_GUIDE.md) for a step-by-step.

```bash
nextflow run foi-bioinformatics/nanometanf -r 1.5.0 \
    --input samplesheet.csv \
    --outdir results \
    -profile conda
```

For real-time runs:

```bash
nextflow run foi-bioinformatics/nanometanf -r 1.5.0 \
    --realtime_mode \
    --kraken2_enable_incremental true \
    --max_concurrent_batches 4 \
    --max_classification_forks 8 \
    --nanopore_output_dir /path/to/fastq \
    --kraken2_db /path/to/db \
    --outdir results \
    -profile conda
```
