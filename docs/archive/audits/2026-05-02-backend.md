## 7. Known issues triaged

### 7.1 `lib/BatchUtils.groovy:28` rewrite (count-or-timeout flush)

**Verdict: implementation is sound, with one minor latent concern.**

Read of `lib/BatchUtils.groovy:1-122`:

- The `timeoutSeconds <= 0` short-circuit at `:48-50` returns the previous count-only `buffer(size: ..., remainder: true)` -- preserves backward compatibility cleanly.
- The `subscribe`-based consumer at `:98-118` is the right primitive. The doc-block at `:19-27` explains why a previous attempt to use `subscribe` purely as a side-effect listener failed (Nextflow's `subscribe` is built on `Dataflow.operator` and acts as a competing consumer of the upstream channel).
- The `synchronized(lock)` block guards the size-check + drain pattern at `:100-105` against the timer thread racing the subscribe thread on `buffer.size() >= batchSize`. `ConcurrentLinkedDeque` itself is thread-safe, but the **size-then-drain** sequence is a TOCTOU without the lock, so the lock is required.
- `Timer('batch-timeout-flush', /* daemon */ true)` at `:81` is correctly daemonized so the JVM cleanup is not blocked here.
- `onComplete` cancels the timer at `:116` and emits a `PoisonPill` at `:112` so downstream channels know to terminate.

Two observations:

1. **`scheduleAtFixedRate(period = timeoutSeconds * 1000L, initialDelay = periodMs)`** at `:90`. The doc-comment at `:76-79` explains the symmetric initial delay is intentional ("the first flush only fires after timeoutSeconds"). This is correct but has the consequence that on a low-throughput run, the very first batch is delayed by exactly `timeoutSeconds`. That's the documented intent, so no change needed; just be aware that operators tuning `params.batch_timeout` should expect the first-batch latency to equal the configured timeout.
2. **The lock is also held during `ch_output.bind(batch)`** at `:69`. `DataflowQueue.bind` should not block under normal circumstances, but if a downstream operator is slow and back-pressure builds, the timer thread could hold the lock for the duration of a bind. In practice this is extremely unlikely because downstream is a `flatten` + `map` chain on the consumer side. Not flagged as a bug; flagged so the next operator is aware.

Recommended action: none required. The `lib/BatchUtils.groovy:28` rewrite is correct.

### 7.2 `bin/run-nf-tests.sh:72` -- NXF_VER pin to 25.04.7

**Verdict: mitigation is still needed; pin should remain.**

Read of `bin/run-nf-tests.sh:1-84`:

- The header doc (`:7-30`) explains the upstream watchPath JVM cleanup hang in 25.10.4.
- The pin at `:72` (`: "${NXF_VER:=25.04.7}"`) is conditional, so callers can override.

The pin therefore reduces but does not eliminate the hang surface. The two affected tests were tagged `hangs-on-jvm-cleanup` in cycle 9 (2026-04-26) per the doc.
- Upstream issue tracked in `docs/upstream-issues/26-watchpath-cleanup-hang.md` (referenced at `:50-53`).
